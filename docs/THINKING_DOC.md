# AccountPulse - Thinking Document

**What it does and for whom.** AccountPulse is a live CRM for a customer success manager who must hand two accounts to their manager on Monday. It reads both accounts through the Questathon MCP, caches everything, and answers five questions per account: book value, power map, first three actions, risks, and knowledge gaps. Every number and claim shows the evidence ID it came from; clicking an ID opens the underlying record.

**How it decides (the rules).**
- *Book value:* a deal counts as qualified only if its stage is qualified, cleared or agreed and the API gives a value. That value is the API's "worth up to" ceiling, not a booked amount, so it is labelled "up to". It counts as *verified* only if the evidence the API lists on the deal includes a verified fact or a file AND the deal has no open blocker; verified evidence with an open blocker is shown in its own "blocked" bucket, and claim/told-only evidence is "unverified". Claims and "told" facts never count as verified. Deals without qualification are shown as uncertain, separately. The morning snapshot ($264,398) is shown only as a reconciliation reference, never as a source for totals.
- *Power map:* the API has no role fields, so decision-maker/payer come only from the "This morning" page (labelled "Morning snapshot (not API)"); blockers come from the API deal record. People carry their API relationship status. Missing roles are shown as Unknown.
- *Action ranking:* score = deal value + stage + deadline urgency (deadlines flagged soon or passed score highest) + blocker + cold or unknown decision-maker. Live events that need a customer reply outrank routine deals. Owners and dates are never invented: they show "Unassigned" or "Requires confirmation" unless the data states them. Probability is shown only if the API supplies it.
- *Risks:* RED/AMBER/GREEN from deadlines, guarded or never-met stakeholders, deals with blockers, unrenewed renewals, and live events (personnel change, unanswered customer request, usage drop). Each risk lists its reason, impact and evidence.
- *Gaps:* unknown roles, unmet people, unverified qualified values, missing values and event-driven unknowns (e.g. the unnamed successor), each with who could answer and a question to ask.
- *Staying live:* a single scheduler enforces 62 seconds between calls (fetch accounts, signals, paperwork once; then alternate get_signals and whoami). New signals are detected automatically, create risks/actions/notifications, and appear without a reload. Notes are queued and written through write_note.

**What it does not do yet.** Live-event rules are keyword-based, so an unfamiliar event type gets a generic AMBER "review" risk. Usage drops are computed only from the usage file attached to the signal, not from the full paperwork history. New accounts (e.g. Kestrel Estates) are ingested through get_new_account and shown with the same views, but are not reconciled to the morning book. Deadlines use the game clock ("moves left"), not calendar dates. Decision-maker/payer roles are not in the API, so only the ones on the morning page are shown. File contents (get_file) are not read, only file ids and titles.
